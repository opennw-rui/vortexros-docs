# 接口处理顺序

策略的 inbound、outbound 相对于绑定接口，不按配置输入的先后排序。物理二层端口、Vlanif三层网关和隧道内层接口处在不同路径，不能把它们视为同一个绑定点。

## 已绑定功能的相对顺序

下表列出产品功能之间明确规定的先后关系；只有已经配置并启用的功能才参与处理。

| 路径 | 相对顺序 | 配置影响 |
| --- | --- | --- |
| IPv4三层入方向 | ACL → MQC → TCP MSS → NAT Policy → 路由查找 | 入方向 ACL与分类器看到入方向转换前的地址；MQC重定向使用此时匹配到的流量 |
| IPv4三层出方向 | NAT Policy → ACL → MQC → TCP MSS → 接口限速 | 出方向 ACL与MQC可能看到转换后的地址；前面的丢弃不会进入后面的统计 |
| IPv6三层入方向 | ACL → MQC → TCP MSS → 路由查找 | 不能套用IPv4 NAT的地址匹配预期 |
| IPv6三层出方向 | ACL → MQC → TCP MSS → 接口限速 | IPv6业务还需允许必要的邻居发现和路径MTU反馈 |
| 二层IPv4/IPv6入、出方向 | 对应方向的ACL → MQC | 作用于桥接端口的报文，不等同于在Vlanif上配置三层策略 |

uRPF用于源地址路径核对；隧道封装、分片重组、GSO、网卡卸载等还可能参与处理。它们不是本表中省略后就不存在的固定步骤。不同接口与功能组合不能用一条简化的总流水线代替；尤其不要根据GSO或分片报文的计数推断应用层连接数。

## 真实组合结果

同一类转发UDP在入方向被标记DSCP20，随后出方向被标记DSCP10，接收端看到最终ToS0x28。只启用入方向时为0x50，撤销后为0。入方向ACL改为拒绝后，流量在MQC前停止；将同一条规则改回permit后恢复。完整配置与撤销见[MQC案例](../examples/mqc.md)。

ACL是无状态过滤。TCP established只匹配ACK/RST等控制位，不为反向流量创建状态。NAT会话与ACL许可也不是同一件事：已有NAT会话不保证报文能通过后面的ACL。

## 配置与排障

1. 先用接口、路由和健康查询确认基础路径可用。
2. 核对策略绑定的接口、地址族及方向。涉及NAT时，分别写清转换前后的地址与端口。
3. 用 `display acl`、`display traffic classifier`、`display traffic behavior`、`display traffic policy` 和 `display nat-policy` 核对对象；配置存在不等于报文命中。
4. 保留一条应放行的对照流量，再验证拒绝、限速或改写。没有收到报文时，同时检查数据面健康，避免把接口或服务中断误判为策略生效。
5. 撤销时先解除引用，再删除对象，提交后再次验证新流量。

ICMP发送禁止只作用于本机生成的指定消息，不能替代转发ACL。其实际接口语义、对路径MTU发现的影响与MPLS回程说明见[ICMP发送控制](icmp-send.md)。


## NAT、MQC与MSS组合

实际组合验证中，出口接口PAT先将内部源203.0.113.2转换为198.51.100.1；同一出口的MQC按转换后的198.51.100.1/32匹配并设置DSCP30，TCP MSS设置1200。接收侧SYN中源地址已转换、ToS为0x78、MSS为1200，TCP数据160768字节完整送达。

只撤销NAT绑定后，再次传输4096字节完整送达；源地址恢复203.0.113.2，MQC的转换后源地址条件不再命中，ToS恢复0，而尚未撤销的MSS仍为1200。最后分别撤销MQC与MSS。该结果验证这些功能的相对处理关系，不代表任意插件组合的吞吐或绝对节点顺序。
