接口重建与重放

配置存在但接口列表为空

开发分支已在原 P2 隔离拓扑复现持续空接口：接口反复重建后，旧多播订阅未从 RIP socket 释放，达到内核订阅上限时，新接口入组返回 No buffer space available，RIP 接口无法启动。修复已纳入 v0.29-dev 候选单文件安装包，并用该包在 QEMU 完成定向验证；尚未在 GitHub 发布。

出现时先保留异常进程，记录 display rip 1 interface、display rip 1 route、health check、运行配置及对应Linux接口的地址、管理状态、carrier和VRF。开发人员还需取得RIP自身的接口及定时器状态；只看Zebra接口正常，不能证明RIP内部也正常。完成采集后再决定恢复操作。

已保存异常进程的接口、地址、定时器、连接状态和 core。修复在 FRR 的退组入口释放原 ifindex 对应的订阅，不要求接口仍为 Up，也不要求地址仍存在；没有提高上限或添加自动重启。原 P2 修复后重建接口，RIP PID 不变，3 个接口恢复，订阅资源不再累积。已有 LoopBack 创建、查询和删除验收也增加了订阅释放检查。

区分启动延迟和持续异常

FRR 收到接口 Up 后会延迟约 1 秒启动该接口的 RIP。隔离实测在这一窗口查询时接口表为空；同一进程的接口已匹配 network、仍有启动定时器，随后自行恢复。因此提交或链路恢复后立即的一次空表，不能单独证明故障。超过启动阶段仍持续为空，则应按上面的步骤保留现场，检查多播入组错误，不能用固定等待掩盖异常。

上游依据：FRR #8680。其中接口 Down 时取消旧启动定时器的修复已经包含在配套源码中。

Zebra 重连后的路由恢复

另一种故障表现为 RIP 接口和协议路由仍存在，但 Zebra 重连后 Linux 路由未恢复。它与空接口不同，应同时比较协议表、系统路由表和连通性。

开发分支已采用 FRR #22411 的 RIP 上游修复（3c9a369699d9）。隔离默认实例和 VPN 实例在保留 RIP 进程、只重启 Zebra 后，两条已学习路由自动恢复，两个方向各 3 次 ping 成功，期间没有新的邻居路由更新。此为开发二进制定向结果，已打入后续 v0.29-dev 候选包并用包内程序定向验证，持续空接口的多播订阅释放问题已另行修复，两项均已纳入 v0.29-dev 候选包，尚未更新 GitHub 发布附件。

已取得的定向结果

原 P2 上，保持旧 RIP 进程不变重建数据面接口，实际出现 13 次成功入组、11 次 ENOBUFS、零次退组，接口由 3 个降为 1 个，再持续为空。失败时内部三个接口均已匹配 network，但 running=0 且没有启动定时器。

修复后在同一拓扑保持新 RIP 进程不变再重建接口，旧订阅正常退出，3 个接口及 2 个更新源恢复；创建和删除双栈 LoopBack201 时，socket 选项内存为 144→192→144 字节。对端 CLI 显示 10.97.0.2/32 来自 RIP（preference100、cost2）并进入 FIB，最终稳定探测 3/3 成功。切换附近另有首包丢失记录，不宣称无损切换。

上述修复已进一步用 v0.29-dev 最终候选包验证：控制层 0.29~dev、FRR 1.7-dev；接口重建、订阅释放及默认/VPN 路由重放通过。候选包尚未发布。旧的历史异常进程没有内部快照，不能把同类复现说成已经读取过旧进程的确切失败状态。
